## 1. Functional Requirements

### 1.1 Authentication & Session Management

- **FR-001** The system shall authenticate users via username/email and password using session-based authentication (server-side session, HttpOnly + Secure + SameSite=Strict cookie).
- **FR-002** The system shall enforce session expiry after 30 minutes of inactivity (configurable) and require re-authentication thereafter.
- **FR-003** The system shall allow a user to explicitly log out, invalidating the server-side session immediately.
- **FR-004** The system shall lock a user account for 15 minutes after 5 consecutive failed login attempts.
- **FR-005** The system shall provide an architecture hook (pluggable auth provider) for a future **on-premises Active Directory (LDAP/Kerberos) or ADFS/SAML** integration without changing the session/authorization model downstream, and shall never integrate with a cloud-hosted identity provider (see 08-system-architecture.md §7, 11-security-architecture.md §2).

### 1.2 User & Role Management

- **FR-010** The system shall allow an Administrator to create, edit, deactivate, and reactivate user accounts.
- **FR-011** The system shall allow an Administrator to assign exactly one of six roles (Administrator, StCd Owner, Engineer, Reviewer, Chief Engineer, Viewer) per user; only an Administrator creates users, and an StCd Owner may move a user between Viewer, Engineer and Reviewer (FR-156, BR-024).
- **FR-011a** The system shall allow an Administrator to tag an Engineer-role user with one or more Engineering Domains (06-data-dictionary.md §10), used to route Cross-Domain Sign-Off (§1.3a).
- **FR-012** The system shall prevent deactivation of the last active Administrator account.
- **FR-013** The system shall allow a user to change their own password, enforcing the password policy in 11-security-architecture.md §4.
- **FR-014** The system shall allow an Administrator to force a password reset for any user.

### 1.3 Status Code Creation & Editing

- **FR-020** The system shall allow an Engineer or Administrator to create a new Status Code by specifying a Functional System Group and a Functional Subgroup — **both mandatory, corrected 2026-09-17: Functional Subgroup is never optional** — and all mandatory attributes defined in 06-data-dictionary.md.
- **FR-021** The system shall NOT assign a fixed Status Code Identifier while a code is in Draft. It may offer a non-binding preview of the likely next identifier for display purposes only (`GET /status-codes/next-available`); the identifier is allocated exactly once, atomically, at the Draft→Review transition (05-governance-handbook.md §2, 07-database-design.md §7a).
- **FR-021a** The system shall allow an Administrator to override the automatically allocated identifier for a documented migration/reservation case, with the reason logged.
- **FR-022** The system shall reject creation or save of a Status Code Revision if any mandatory attribute is missing, malformed, or fails cross-field validation rules (06-data-dictionary.md "Validation" column).
- **FR-023** The system shall prevent creation of a duplicate `status_code_identifier` (unique constraint; see 07-database-design.md).
- **FR-023a** The system shall require at least one Turbine Platform to be selected before a revision can be submitted for Review.
- **FR-024** The system shall allow an Engineer to save an in-progress Status Code as Draft an unlimited number of times without triggering workflow transitions.
- **FR-025** The system shall NOT allow direct in-place editing of a Status Code Revision that is in Review, PendingApproval, Approved, Released, Deprecated, or Archived state; any change requires creating a new Draft revision from the current one (copy-on-write).
- **FR-025a** The system shall treat each of the eight audience-access fields (corrected 2026-09-17: Development, Sales, TCC, Service, Turbine Operator Package, Grid Operator, Service Partner, Customer — replaces the single `access_rights_id`) as a restricted field: an Engineer may propose values while the revision is in Draft, but none is authoritative until confirmed or overridden by the Administrator's Review sign-off (06-data-dictionary.md §2d, SEC-013).
- **FR-026** The system shall allow an Engineer to withdraw/cancel a Draft, Review, or PendingApproval Change Request before it reaches Approved.

### 1.3a Cross-Domain Sign-Off

- **FR-027** The system shall determine, from the field-to-Engineering-Domain ownership mapping (06-data-dictionary.md §2a), which domains are required on a given revision, and shall flag any domain not covered by the originating Engineer's own domain tags as pending.
- **FR-028** The system shall allow the originating Engineer to request sign-off from an Engineer holding a required, pending domain, and shall surface that request on the target Engineer's Dashboard and Change Request list.
- **FR-029** The system shall block Submit-for-Review (422) while any required domain lacks a recorded `DomainSignoff`, and shall only accept a `DomainSignoff` from a user who actually holds the named Engineering Domain.

### 1.4 Change Request & Review Workflow

- **FR-030** The system shall require every creation of a new Status Code and every revision of an existing one to be represented as a Change Request (CR) that carries the proposed revision through the lifecycle.
- **FR-031** The system shall allow an Engineer to submit a Draft CR for Review, which allocates the Status Code Identifier (FR-021), transitions the associated revision from Draft to Review, and notifies eligible Reviewers and the Administrator.
- **FR-032** The system shall present Reviewers and the Administrator with a field-level diff between the proposed revision and the current Approved/Released revision of the same Status Code (or "new code" if none exists).
- **FR-033** The system shall allow a Reviewer to record an independent sign-off (approve or reject) on a CR in Review; rejection requires a mandatory comment and returns the revision to Draft, clearing both sign-off columns.
- **FR-034** The system shall allow an Administrator to record an independent sign-off (approve or reject) on a CR in Review, following the same rules as FR-033, and shall confirm or override any restricted field (FR-025a) at the moment of approval.
- **FR-035** The system shall automatically transition a CR from Review to PendingApproval, atomically with whichever sign-off action is recorded second, once both the Reviewer's and the Administrator's sign-offs are present (in either order).
- **FR-036** The system shall allow a Chief Engineer to record the final Approval decision (approve or reject) on a CR in PendingApproval; rejection requires a mandatory comment and returns the revision to Draft, clearing both prior sign-offs.
- **FR-037** The system shall prevent the Engineer who authored a CR from signing off or approving their own CR at any of the three decision points (Reviewer sign-off, Administrator sign-off, Chief Engineer approval), and shall additionally prevent the Chief Engineer decision from being made by whichever individuals already provided the Reviewer or Administrator sign-off on that same CR (BR-005).
- **FR-038** The system shall allow a Reviewer, Administrator, or Chief Engineer to add comments to a CR at any stage without changing its state.
- **FR-039** The system shall allow an Administrator to reassign or unassign a CR between Reviewers.

### 1.5 Release Management

- **FR-040** The system shall allow an Administrator to create a Release container with a name, target version label, description, and scope filter (e.g. Functional System Group, Functional Subgroup).
- **FR-041** The system shall list all non-sandbox Status Code Revisions in Approved state matching a Release's scope filter as candidates for inclusion.
- **FR-042** The system shall allow an Administrator to include/exclude individual candidate revisions before publishing.
- **FR-043** The system shall, upon publishing a Release, transition all included revisions from Approved to Released, stamp Effective Date, and mark the Release as immutable.
- **FR-044** The system shall prevent modification of a published Release's contents; a correction requires a new Release.
- **FR-045** The system shall allow export of any Release, or of the current set of all Released status codes, in CSV, JSON, XLSX, and PDF formats (XLSX added 2026-09-17), all as flat, table-shaped output (one row per status code), per the role-scoped catalogue-export matrix (11-security-architecture.md §3). Since v4 an export may additionally be shaped by an export profile, an audience, a language and a software version, and ships with a manifest (FR-100–FR-104, FR-107, FR-111). Since v4.10 a Release export is its complete baseline (FR-173).
- **FR-046** The system shall allow export of a Draft/ad-hoc filtered working set, distinctly labeled "Not for distribution — unapproved data," restricted to the StCd Owner and the Administrator since v4.10 (FR-175; before: Engineer/Reviewer/Administrator/Chief Engineer).
- **FR-047** The system shall allow an Administrator, and only an Administrator, to generate a full raw database export/backup, distinct from catalogue export (08-system-architecture.md §6, SEC-015). Since v4 it is requested with `POST` and the Administrator's password (FR-126).
- **FR-048** The system shall prevent a sandbox-flagged revision from ever being added to a Release candidate list or included in a published Release, enforced independently at the service layer and the database layer (07-database-design.md §5).

### 1.6 Deprecation & Archival

- **FR-050** The system shall allow an Administrator (or Engineer via CR, subject to the full three-decision-point cycle) to initiate deprecation of a Released Status Code, requiring a mandatory reason and an optional superseding identifier reference.
- **FR-051** The system shall allow an Administrator to archive a Deprecated Status Code after the configured minimum retention period has elapsed (05-governance-handbook.md §11); Archived codes become read-only.
- **FR-052** The system shall prevent deletion of any non-sandbox Status Code or Revision at any lifecycle state; removal from active use is only possible via Deprecated/Archived states.

### 1.5a Library Import (new 2026-09-17 — reverses the prior "no bulk import" position)

- **FR-048a** The system shall allow an Engineer or Administrator to upload a CSV or XLSX file of status codes for bulk import.
- **FR-048b** The system shall validate every imported row against the same rules as manual entry (06-data-dictionary.md), creating a Draft `StatusCode`/`StatusCodeRevision`/`ChangeRequest` for every row that passes and recording every row that fails in a downloadable error report (FR-048m); a failing row creates nothing.
- **FR-048c** The system shall require every imported row to pass through the full governance cycle (Cross-Domain Sign-Off where applicable, both Review sign-offs, Chief Engineer approval) before it can be Released — import is a faster data-entry path, never a governance bypass (confirmed explicitly by the business; 05-governance-handbook.md §6b).
- **FR-048d** The system shall preserve any legacy/source numbering supplied in the import file as `legacy_reference_number` for traceability, distinct from and never confused with the governed `StCd` identifier.

### 1.5b Subgroup Administration (new 2026-09-17)

- **FR-048e** The system shall allow an Administrator to create a new Functional Subgroup within any Functional System Group, specifying a name and a numeric sub-range.
- **FR-048f** The system shall reject a proposed subgroup sub-range that overlaps any existing subgroup in the same Functional System Group (409), naming the conflicting subgroup, enforced at both the service layer and the database layer (07-database-design.md §5).
- **FR-048g** (new 2026-09-17) The system shall allow an Administrator to create a brand-new Functional System Group, specifying a code (prefix), label, and a numeric range, into any currently free range (confirmed reserved: `10000–10999`, `14000–14999`, `15000–15999`, `16000–16999` — 05-governance-handbook.md §2), without requiring a schema change.
- **FR-048h** (new 2026-09-17) The system shall reject a proposed Functional System Group range that overlaps any existing group's range (409), naming the conflicting group, enforced at both the service layer and the database layer (07-database-design.md §5).

### 1.6a Sandbox Status Codes

- **FR-053** The system shall allow an Administrator, and only an Administrator, to create a Status Code flagged `is_sandbox = true`, drawing its identifier from an isolated `StCd-T#####` band that never overlaps a real Functional System Group range.
- **FR-054** The system shall exclude sandbox-flagged records from default search results, catalogue exports, and Release candidate lists by construction, not by convention (FR-048).
- **FR-055** The system shall allow an Administrator, and only an Administrator, to permanently delete a sandbox-flagged Status Code, and shall reject any deletion attempt against a non-sandbox record regardless of role, enforced at both the service layer and a database trigger.
- **FR-056** The system shall record a `SANDBOX_DELETE` audit entry containing a full pre-delete snapshot of the deleted record, in the same transaction as the delete, so the fact of creation and deletion remains permanently traceable even though the record itself no longer exists.

### 1.7 Search, Filter, and Browse

- **FR-060** The system shall provide full-text search across Status Code Identifier, Title, and Description (ranked and typo-tolerant since v4, FR-148).
- **FR-061** The system shall provide filtering by Functional System Group, Functional Subgroup, Turbine Platform, Lifecycle State, Status Category, Owner, Software Version, and sandbox flag (default excluded), individually or combined; a filter combination can be saved and shared as a link (FR-142).
- **FR-062** The system shall provide sorting on any listed column, ascending or descending.
- **FR-063** The system shall paginate list results with a configurable page size (default 50, max 200).
- **FR-064** The system shall allow a Viewer or higher role to view the complete revision history of any non-Draft/Review/PendingApproval Status Code, including diffs between any two revisions; Draft/Review/PendingApproval-state data is visible to Engineer, Reviewer, Administrator, and Chief Engineer roles only (BR-009).

### 1.8 Audit Trail

- **FR-070** The system shall record an immutable audit log entry for every create, update, state transition, sign-off, approval, rejection, release, deprecation, archival, sandbox create/delete, login, failed login, step-up confirmation, role change, delegation, settings change, evidence, translation, token and webhook change, and export action, capturing actor, timestamp (UTC), entity type, entity ID, action, and before/after field values where applicable (12-audit-compliance.md).
- **FR-071** The system shall allow Administrators (and Reviewers/Chief Engineers, read-only, for records they are entitled to act on) to search and filter the audit log by actor, entity, action type, and date range.
- **FR-072** The system shall prevent any user, including Administrators, from editing or deleting audit log entries through the application.
- **FR-073** The system shall retain the audit trail for a deleted sandbox record indefinitely, even though the application provides no means of retrieving the record itself once deleted (FR-056).

### 1.9 API

- **FR-080** The system shall expose a versioned REST API (`/api/v1/...`) covering Status Codes, Revisions, Change Requests (incl. sign-off/approval/domain-sign-off endpoints), Releases, Users, Lookups, and Audit Log read access, per 09-api-specification.md (161 operations in v4.10; `docs/artifacts/openapi.yaml` is the contract and a test fails if the code and the contract differ).
- **FR-081** The system shall enforce the same role-based authorization on the API as on the UI; the API is not a privilege-escalation path.
- **FR-082** The system shall support API pagination, filtering, and sorting equivalent to the UI list capabilities (FR-061–FR-063).
- **FR-083** The system shall be reachable only from the internal corporate network in every deployment; no endpoint shall be exposed to the public internet, and no request shall be proxied through or dependent on a public-cloud service.

### 1.10 Concurrency & Data Integrity (v4 — I-01, I-04, I-12, I-25; EPIC-17)

- **FR-090** The system shall detect conflicting edits of a Draft: every revision carries a `row_version` that increases on each save and an `updated_at` stamp; an edit that names a stale `expected_row_version` (or `expected_updated_at`) is rejected with 409 and changes nothing, and the edit form re-shows the user's entries beside the current values (NFR-007a). An edit that names neither is accepted (backwards compatible).
- **FR-091** The system shall *warn, never block*, when `status_code_for_repeated_error`, `related_status_codes` or `superseded_by_status_code_id` point at a code that is unknown, Deprecated or Archived, or at the code itself. The warnings are returned with the saved revision, shown after saving, and listed on the code's detail page and on the change request.
- **FR-092** The system shall show, on every code, a **Where-used** list of the other codes whose current revision refers to it (repeated-error pointer, related codes, supersession, platform variant), and shall require the requester of a deprecation to acknowledge the live dependants (`acknowledge_dependants`) before the request is created.
- **FR-093** The system shall show existing codes of the same Functional Subgroup with an identical or similar title when a code is created or imported ("did you mean to revise StCd-…?"). The check is a warning; it never blocks a save or an import row.
- **FR-094** The system shall allow an Engineer or Administrator to create a **platform variant** (e.g. 4XM from a 3XM code): a new Draft that copies the latest decided revision for another turbine platform, linked through `platform_variant_of_status_code_id`, with the family shown on both detail pages.

### 1.11 Library Import Toolkit (v4 — I-05, I-32; extends 1.5a)

- **FR-048i** The system shall offer the import template for download (CSV: the exact headers; XLSX: headers, instructions and the lookup codes), and the unmodified template shall import cleanly.
- **FR-048j** The system shall offer a **dry run** that validates a file with the full import rules and reports every problem per row and column (value, problem, how to fix) and every warning, while creating nothing — not even an import job.
- **FR-048k** The system shall offer an **update mode** keyed on `legacy_reference_number` (unique within a Functional System Group): a changed row revises the already-imported open Draft in place, or opens a new revision of an already-Released code; an unchanged row is skipped; a row without a match is created; a code that is in review, has another owner, or would change group or subgroup is reported as an error on that row.
- **FR-048l** The system shall provide a **reconciliation report** — legacy rows imported, in review, approved, released, retired and, given an expected total or the uploaded legacy master list, still missing (with the missing legacy numbers named).
- **FR-048m** The system shall provide each import job's error report as CSV and as XLSX, with one line per problem (row, column, value, problem, how to fix); values that start with a formula character are neutralised (SEC-024).
- **FR-048n** The system shall process files above a configurable row threshold (default 300) in a background worker and show progress (`processed_count`, percentage) on the job; the upload returns 202 and the job ends COMPLETE or FAILED, never silently stuck.

### 1.12 Publication, Release Integrity & Software Versions (v4 — I-02, I-03, I-06, I-07, I-15, I-24, I-27; EPIC-18, EPIC-20, EPIC-22)

- **FR-100** The system shall let an Administrator define **export profiles** — named column sets with header labels and an optional default audience and language (seeded: *Service manual*, *SCADA tag list*, *Customer list*) — as data, and shall let any export, release export or bundle use one.
- **FR-101** The system shall never truncate cell text in the PDF export: cells wrap over several lines, the header row repeats on every page, and a title page shows the release, version, effective date, filters, row count and the content digest.
- **FR-102** The system shall allow an export to be scoped to one of the eight audiences: only codes whose Administrator-confirmed value for that audience is *visible* are included, and the other audiences' columns are omitted. Visibility is data on each access vocabulary value (`audience_visible`); a code with no value for the audience is hidden (decision D-02, BR-016).
- **FR-103** The system shall accompany every export of a Release with a **manifest** (release, scope, row count, SHA-256 of every file, content digest, generator, timestamp, applied profile/audience/language/version), signed with HMAC-SHA-256 when `MANIFEST_SIGNING_KEY` is configured, and shall record each export with its hash. The export can ship as a ZIP bundle containing the data file, `MANIFEST.json` and the release notes.
- **FR-104** The system shall verify a file against a manifest without the database — in the UI and API (`/exports/verify`) and on the command line (`flask verify-export`) — reporting the SHA-256, the matching recorded exports, whether the file is listed and whether the signature is valid, invalid or absent.
- **FR-105** The system shall generate **release notes** for every published Release against the previous published Release: codes *added*, codes *changed* (with the field-level diff of FR-032) and codes *deprecated*, as Markdown, CSV and PDF.
- **FR-106** The system shall maintain an ordered vocabulary of **controller software versions**; each revision may declare an inclusive from/to version range (either end open) and each Release targets one or more versions, which an Administrator sets before publishing (decision D-01).
- **FR-107** The system shall answer "which Released codes apply to version X" and "what was added, removed and changed between versions X and Y" (applicability matrix), and shall allow any export or bundle to be limited to one software version.
- **FR-108** The system shall generate, from any Release, an **offline lookup bundle**: one self-contained HTML file with the codes embedded and a search box, loading nothing from the network, listed in the manifest.
- **FR-109** The system shall let an Administrator stamp a **planned effective date** and a **planned deprecation date** on the current revision (audited); the release builder and the publish response warn — never block — when an included revision's planned effective date is still in the future.
- **FR-110** The system shall hold translations of title and description per language (English is the source; German is seeded) with a status of MISSING, DRAFT or APPROVED. A translation is saved only against an Approved or Released source revision, approved by a Reviewer or Administrator who is not the translator (BR-018), sent back to DRAFT by any edit, and carried over from the previous revision as DRAFT on request.
- **FR-111** The system shall export in a chosen language using approved translations only, falling back to the source text unless the export is *strict*, and shall list the codes still lacking an approved translation (worklist).

### 1.13 Workflow Aids & Governance Extensions (v4 — I-08, I-10, I-11, I-13, I-14, I-16, I-17, I-23, I-30; EPIC-04, EPIC-19, EPIC-23)

- **FR-120** The system shall show how long every change request has waited at its current stage, in business days (Monday–Friday, no holiday calendar), and shall mark it amber or red against Administrator-configured thresholds (defaults: review 3/5 days, approval 2/3 days).
- **FR-121** The system shall create **in-app notices** for whoever holds the next decision (including anyone covering for them, FR-125) on a stalled request, at most once per user, request, stage, level and day, through `flask send-reminders`; if an SMTP relay is configured (decision D-04) the same text is also mailed. A mail failure never breaks the triggering action.
- **FR-122** The system shall give Administrators a list of stalled change requests with one-click reassignment (FR-039).
- **FR-123** The system shall show Administrators and Chief Engineers the business-case KPIs: median business days from submission to approval (target ≤ 7), median cross-domain turnaround (target ≤ 3), share of Released revisions with a complete audit trail (target 100 %), the age distribution of open requests and the codes whose owner is no longer an active user.
- **FR-124** The system shall let Administrators, Engineers and Chief Engineers group change requests into a **change set** for one controller software release and let reviewers decide several of its requests in one sitting. Each request is still decided by its own service call with its own segregation-of-duties check, comment and audit entry; a request the actor may not decide is reported as skipped and never blocks the others (BR-005 is unchanged).
- **FR-125** The system shall let a Reviewer, Administrator or Chief Engineer name a **delegate** for a date range (an Administrator may do so for anybody). The delegate acts as themselves; the audit entry names both; delegation grants the decision actions of the delegated role only, never user administration; segregation of duties applies to the delegate personally (BR-017, decision D-08).
- **FR-126** The system shall require the actor's password again (**step-up**) for Reviewer and Administrator sign-off, Chief Engineer approval, publishing a Release and the full-database export; a missing password returns 403 `step_up_required`, a wrong one 403 `step_up_failed`; both outcomes are audited and the same password prompt covers a whole change-set decision (decision D-07, SEC-026).
- **FR-127** The system shall let a Reviewer, Administrator or Chief Engineer comment on one specific field of a change request in Review or Pending Approval; the author sees the open comments inline and marks them resolved.
- **FR-128** The system shall let an Administrator maintain a **review checklist** per Functional System Group (or for all groups); an approving Reviewer must confirm every active item that applies, and the confirmed wording is stored with the sign-off.
- **FR-129** The system shall show the open reviews per Reviewer and shall assign the least-loaded available Reviewer on request, or automatically at submit when the Administrator enables it; a Reviewer who is out of office (FR-125) is skipped.
- **FR-130** The system shall let the author or an Administrator attach **evidence** to an open change request (PDF, PNG, JPG, TXT, LOG, MD, CSV, XLSX, DOCX; at most 10 MB and 20 files each), checked against the claimed type, stored outside the web root, downloadable only as an attachment by the working roles and removable only while the request is a Draft (SEC-024).
- **FR-131** The system shall carry the optional fields *remedy text*, *affected component* and *standard references* on a revision; they have an "Any" owner (06-data-dictionary.md §2a), so they never gate Cross-Domain Sign-Off, and they appear in the matching export profiles and the offline bundle.

### 1.14 Insight, Integration & Hub Consolidation (v4 — I-19, I-26, I-28, I-29, I-31, I-36; EPIC-16, EPIC-24)

- **FR-140** The system shall provide a **catalogue health report**: expected-but-missing optional data (remedy text, component, software-version range, audience access), inconsistent combinations (INFO with an alarm; repeat count without escalation code or the reverse; repeat window without count; planned deprecation date passed), unused numbers inside a band, and the upcoming planned dates.
- **FR-141** The system shall show how full every subgroup's number band is and alert Administrators, Reviewers and Chief Engineers when at most N percent or N numbers remain (defaults 15 % / 20), and shall preview the remaining capacity on the New Status Code form. On the health page the rows of Main Controller groups are blue and those of Hub Controller groups light blue, each with an MC or HC chip, so the two numberings can be told apart at a glance.
- **FR-142** The system shall let users save a search (filters and visible columns) under a name, choose the columns of the list, and share the same view as a URL.
- **FR-143** The system shall let an Administrator or Chief Engineer import anonymised occurrence counts per status code and period (CSV/XLSX with `status_code_identifier` and `occurrences`) and report the Released codes that never fired and the most frequent ones, flagging those without remedy text.
- **FR-144** The system shall let an Administrator issue **scoped, expiring API tokens** (`catalogue:read`, `changes:read`; at most 365 days; stored only as a hash; shown once; revocable). A token authenticates `Authorization: Bearer cscm_…` on the read-only endpoints that declare its scope, with Viewer-level visibility, and can never write (SEC-027).
- **FR-145** The system shall provide a **change feed** (`GET /changes`) of releases, deprecations, reinstatements and archivals in audit order, paged with a `since_id` cursor and supporting `ETag`/`If-None-Match`.
- **FR-146** The system shall let an Administrator register **webhooks** on `release.published`; a delivery carries an HMAC-SHA-256 signature, goes only to a private or loopback address, does not follow redirects, is recorded with its outcome, and can never block or fail the publish (SEC-028).
- **FR-147** The system shall support the Hub → Main Controller consolidation of assumption A-008: create a Main Controller Draft from an Approved or Released Hub Controller code (new MC number at submit, the HC identifier kept as the legacy reference, mapping recorded), report every Hub code with the state of its replacement, and open deprecation requests for all Hub codes of a group whose replacement is Released.
- **FR-148** The system shall rank search results by relevance (a title hit outranks a description hit) and tolerate small spelling errors ("convertor" finds "converter"), falling back to substring search where the SQLite build lacks FTS5.

### 1.15 Operations & Usability (v4 — I-09, I-18, I-21, I-22, I-33, I-34, I-35; EPIC-25)

- **FR-150** The system shall back the database up with SQLite's online-backup API (`flask backup-db`), keep a configurable number of generations, and **prove** each backup is usable (integrity check, restore into a scratch database, row-count comparison, audit-chain check), writing the result to a status file that the readiness probe and the Administrator view read.

### 1.16 Status Code Import from Generated Programs (v4.2 — extends 1.5a; EPIC-14)

The generated controller programs (`PROGRAM StCd_<n>`, IEC 61131-3 Structured Text, written by the status code generator) already carry every status code of the controller: its number, name, delays, repeat rule, alarm and availability settings, subsystem programs and user-group levels. These requirements let the business bring new codes into the catalogue **from the `.st` files alone**, several at a time, without bypassing governance (FR-048c). The reader never executes or compiles anything; it scans the text (`app/importers/stcd.py`).

- **FR-048o** The system shall let an Engineer or Administrator upload several `StCd_<n>.st` files at once, a whole folder, or one ZIP archive of them, read every `PROGRAM StCd_<n>` in them (UTF-8, falling back to the generator's CP1252) and report files that hold no program or exceed the size limit instead of failing the upload (SEC-031).
- **FR-048p** The system shall show a **preview** before anything is created: one line per program with its new identifier, legacy number, controller, name, the group and subgroup its number lies in, a state (*ready*, *already in the catalogue*, *blocked*), every problem and every warning, and shall let the user tick any subset (select all, filter by text) for creation. The preview writes nothing except the user's staged copy of the upload.
- **FR-048q** The system shall **reserve** the number a program carries for the Draft created from it (`status_code.reserved_identifier`): the identifier issued at Submit for Review is exactly that number, the sequence allocator skips reserved numbers, an Administrator override is refused for a reserved code, and the database refuses a second reservation or the issue of a reserved number to another code (BR-023).
- **FR-048r** The system shall place each imported code in the Functional System Group and Subgroup whose band holds its number (`NumberingService.band_of`); a number no active subgroup covers, or a number in a Hub band for a Main Controller program (or the reverse), blocks that program with a message naming the missing band.
- **FR-048s** The system shall treat the number in a Hub Controller file as the **legacy** Hub number and take the new number from the numbering table (`hc-numbering-proposal.xlsx`, shipped as `app/importers/data/hc_numbering_mapping.csv`): proposal 1 (five-digit, the default) or proposal 2 (inside the Main scheme), chosen per upload; a legacy number missing from the table blocks the program. A file is a Hub file when it is uploaded as such or, by default, when its number is 10000 or higher.
- **FR-048t** The system shall create every ticked, still-ready program as an ordinary Draft status code with its change request (`cr_type = IMPORT`), filling the attributes the catalogue has (title, availability group, alarm, set and reset delay, repeat rule, snapshot, zero-load operation, the eight subsystem programs it has columns for, the programs the set condition refers to as related codes), and shall put **all Drafts of one confirmation into one new change set** (I-11) so the batch is reviewed and decided together; every Draft still needs Cross-Domain Sign-Off, both Review sign-offs and Chief Engineer approval (FR-048c, BR-015). The status category is not in a program: the uploader chooses one for the batch.
- **FR-048u** The system shall provide the **legacy → new mapping**: for every catalogue code that carries a legacy number, the legacy number (Main or Hub), the identifier it was issued or has reserved, its title and state, with filters and a CSV/XLSX export, for internal roles (not Viewers). The mapping runs from legacy to new only: the new library holds more codes than the old one, so a code without a legacy number is normal and counted as *n/a*, and no reverse lookup is offered. The mapping is the code's `legacy_reference_number` read with its controller type; there is no second copy to keep in step.
- **FR-048v** The system shall keep, for every imported code, its **provenance** — source file name, SHA-256 of the file, program number and line, and every attribute parsed from it as JSON, including those the catalogue has no column for yet (user-group levels, the remaining subsystem programs) — and shall store the program's `PrgIdx_GUi` when it is free (`status_code.prg_idx`, 06-data-dictionary.md §1), warning otherwise.
- **FR-048w** The system shall re-check every ticked program when the user confirms (the catalogue may have changed since the preview): a program that is meanwhile present, or conflicts with a number, a legacy number or another program of the upload, is refused with a message and nothing is created for it; the rest proceeds. Files above the background threshold (FR-048n) are processed in a worker with progress.
- **FR-048x** The system shall, in the preview of an import from program files, also recognise programs whose number is already in the catalogue and say what they would do: **unchanged** (nothing), **changed** — the fields in which the file differs are listed, and the program can **update the open Draft** in place or open a **new revision** of an Approved or Released code — and **withdrawn**, a code whose change request was withdrawn and which can be **restored** as a new Draft on the same number. A changed or withdrawn program is never ticked by default; the user chooses. A code in Review, Deprecated or Archived is reported as blocked. The result joins the batch change set like a new program.

### 1.17 Roles and Languages (v4.3 — EPIC-04, EPIC-25)

Every language name reads **country letters on the left, the name, and the national flag on the right** (`GB English 🇬🇧`, `DE Deutsch 🇩🇪`, `SA العربية 🇸🇦`, `IN বাংলা 🇮🇳`, `PK اردو 🇵🇰`, `ES Español 🇪🇸`, `DK Dansk 🇩🇰` …); in the language menu of the top bar the flag is drawn as an image, because Windows shows flag emoji as two letters, and the menu scrolls. The Indian languages carry the flag of India, Urdu that of Pakistan, Arabic that of Saudi Arabia, Spanish, Italian and Danish those of Spain, Italy and Denmark, Georgian that of Georgia. Arabic and Urdu are written right to left: the page is mirrored (`dir="rtl"`). French, Hindi, Arabic, Spanish, Italian, Danish and Georgian cover the most visible text (top bar, navigation, login, dashboard, status code list and the role names); the ten languages after Arabic cover about sixty strings (top bar, navigation, login, role names); all other text falls back to English, and none of the translations has been reviewed by native speakers. What is translated and what never is — identifiers, numbers, stored codes, audit entries, the content of a status code outside the approval workflow — is fixed in `10-ui-ux-specification.md` §10a.
- **FR-158** The system shall let an Administrator **view** a user (profile, role, domains, last sign-in and what the account has done in the tool), **edit** the user, **deactivate** and **activate** the account with a button, and **delete** an account — in the user list and on the user's page. A deactivated account cannot sign in and an open session ends with its next request; nothing it did is lost. Deletion needs the Administrator's own password (SEC-026), is refused for the Administrator's own account and for the last active Administrator, and works for every account (BR-025): an account that nothing else points at is removed, one with history is erased — its name, address and password go and it leaves every list, but the row stays so that everything it did keeps its author. The audit log is never changed. The StCd Owner sees the list and each user's page but has none of these buttons except the role change of FR-156.
- **FR-159** The system shall let an Engineer or Administrator **select several change requests and withdraw them in one action** (the list *My Change Requests* and `POST /change-requests/withdraw`). Every request goes through the single-request rules — only its author, only while it is a Draft, in Review or waiting for approval — and has its own audit entry; one that cannot be withdrawn is reported and does not stop the others.
- **FR-160** The system shall make clear what a withdrawal does. The withdrawn revision and its change request are deleted and their content is kept in the audit entry (FR-026). A code that is left with no revision and never received its identifier gives back what it held — the number an import reserved, its legacy number and its PrgIdx_GUi — so the same program can be imported again; a code that already has its identifier keeps it (BR-001, BR-026) and can be restored from its program file (FR-048x).
- **FR-161** The system shall keep every interface translation checkable by a native speaker: a generated document ([26-translations.md](26-translations.md)) lists every string of the interface with a stable id, the screens that show it, the English source and each language's translation, per language with its coverage and a fingerprint of the catalogue; a generator (`scripts/gen_translations_doc.py`) writes one review sheet per language (XLSX: current translations with a verdict column of OK / CHANGE / UNCLEAR, a proposal and a comment, the strings still missing, and a checklist); the review itself is done in the application (FR-164), which records a completed review with the fingerprint of the version reviewed and shows a language as not reviewed, in progress, reviewed, or changed since the review. A test keeps the document equal to what the generator produces from the code. How the status code manuals reach every designated language, and what is still open, is the concept of that document (sections 4 and 8).
- **FR-162** The system shall keep a user's **e-mail address fixed** once the account exists. The address is the stable identity of the person (it is what the Windows sign-in matches, FR-163): it is entered when an Administrator creates the user (lower-cased, checked for form and for duplicates) and can never be edited — not in the user form, not through `PUT /users/{id}`, which answers 422 for a body that carries an `email` at all, and not in the database, where the trigger `trg_user_email_immutable` aborts any update of `user.email` that changes it. A person who needs another address gets a new account; the old one is deactivated (BR-025).
- **FR-163** The system shall support **sign-in with the Windows account** and let a developer simulate it. `AUTH_MODE` is `password` (default), `windows` or `both`. In Windows mode the organisation's gateway (IIS or ARR with Windows authentication, Apache with Kerberos, nginx with spnego — any on-premises proxy that authenticates against Active Directory) passes the user in the header `WINDOWS_AUTH_HEADER` (default `X-Remote-User`); the application believes the header only from an address in `WINDOWS_AUTH_TRUSTED_PROXIES` and ignores it from anywhere else. The identity is matched with an active account **by e-mail address** (`name@corp.example`; `CORP\name` becomes `name@WINDOWS_AUTH_EMAIL_DOMAIN`, else the user name); nobody is created on the fly, an unknown or deactivated Windows user is refused with a clear message, and every sign-in and refusal is audited like a password sign-in. In `windows` mode the password form, the password change and the self-service password pages are switched off (API: 403 `password_login_disabled`). **Simulation for development:** with `WINDOWS_AUTH_SIMULATE` (on in the development configuration) the login page offers *Sign in as Windows user*, where the developer types the identity the gateway would have supplied; it runs through the same code as a real header, so what works there works behind the gateway. The production configuration refuses to start with the simulation switched on or with an unknown `AUTH_MODE`. Endpoints: `GET /login/windows`, `POST /login/windows/simulate` (development only), `POST /api/v1/auth/windows`.
- **FR-164** The system shall let native speakers **review the interface translations in the application itself**, in a section of its own (*Translations*, S42 to S44). An Administrator or StCd Owner **assigns reviewers** to a language (any active account; an external native speaker gets a Viewer account that sees only this section). A reviewer sees one row per string — screens, English, current translation — and answers OK, CHANGE with a proposal (at most 1,000 characters, the `%(name)s` placeholders of the English text kept) or UNCLEAR with a comment; strings without a translation can be translated on the way; answers are saved page by page, a completed XLSX sheet can be uploaded instead, and the review is **completed** only when every translated string has a verdict. The completion is recorded with the date and the fingerprint of the version reviewed. An Administrator or StCd Owner **decides** on each proposal — accept (optionally correcting the text), reject or note — never on a proposal of their own; a decision is final. An accepted proposal is an **override** that the application shows at once for that language, without a release; an override can be removed, which restores the shipped text. Assigning, completing, deciding and removing an override are audited (AUD-077).
- **FR-165** The system shall print **every script of its languages in the PDF export**: Latin (with Greek and Cyrillic), Devanagari (Hindi, Marathi), Bengali, Gurmukhi (Punjabi), Gujarati, Odia, Tamil, Telugu, Kannada, Malayalam, Georgian, and Arabic-script text (Arabic in Naskh, Urdu in Nastaliq). The PDF text is Unicode: Noto Sans is the base font, a cell that contains another script also gets the Noto font of that script, the text is shaped with HarfBuzz (conjuncts, vowel signs, joining forms), and Arabic and Urdu cells are laid out right to left and right-aligned; the title page, notice, column headings and footer follow the same rules. The fonts (SIL Open Font License, with the licence text) are bundled in `app/static/fonts/` and the shaping library `uharfbuzz` is a requirement, so a deployment needs no font installation and no internet access. A character that no bundled font draws is replaced by an ASCII stand-in or `?` and never leaves an empty gap; plain Latin text is not shaped and stays fast (NFR-001). The export's language (FR-111) selects Nastaliq or Naskh for Arabic-script text, otherwise the letters decide.
- **FR-166** The system shall keep the **technical nomenclature** — the words of the controller and of the workflow (Status Code, Hub Controller, Set delay, Draft, the roles, the audiences …) — in a vocabulary of its own, apart from the interface translations (FR-164), in a section *Terminology* (S45 to S47). Every term has a stable code, the English text, a category (product, data, state, process, role, audience or never translated), a definition for a translator who does not know the product, and one translation per language. A translation is a **Draft until a second person approves it** (the segregation of BR-018: nobody approves their own proposal; *Send back* needs a note and reopens an approved translation). Everybody who is signed in reads; an Administrator, StCd Owner, Chief Engineer, Engineer or Reviewer proposes; an Administrator, StCd Owner, Chief Engineer or Reviewer approves; an Administrator, StCd Owner or Chief Engineer adds and changes terms, and a changed English text reopens the approved translations of the term. Being the reviewer of an interface language gives no right in the terminology. A term marked *never translated* has no translation. The tool ships 78 terms with a draft translation in each of the 18 languages besides English, taken from the interface catalogue where both contain the word. A consistency check lists the interface strings that contain a term whose translation does not appear in the translation of the string (a hint, not a verdict, because languages that inflect words change the ending), and the vocabulary is exported per language and for all languages as XLSX and CSV (a formula in a cell is neutralised). Every change is audited (`TERM_CREATE`, `TERM_UPDATE`, `TERM_TRANSLATE`, `TERM_APPROVE`, `TERM_REJECT`).
- **FR-167** The system shall translate the **whole interface inventory** into every language it offers: every text a template wraps in `_()`, the role names, the help texts and the sentences of the service layer that a person reads in a flash message (found by reading the source, so none can be missed), 1,093 strings in each of the 18 languages besides English. Only a unit or a code (`d`, `WNEW`, `TCC`) stays as it is, and every placeholder survives in every translation. The catalogues are data files (`app/translations/<language>.json`) that `app/i18n_generated.py` merges: an entry written by hand wins over the file and an accepted override (FR-164) wins over both. The messages of the API stay English (they are part of the contract). The translations of the Indian languages, Arabic, Urdu, Georgian, Spanish, Italian and Danish are **proposals written by the maintainer's tooling and not yet checked by native speakers**; the review of FR-164 is how they become reviewed.
- **FR-168** The system shall store and show **everything the generated controller programs carry** (schema v4.1; [06-data-dictionary.md](06-data-dictionary.md) §2c.1, §2d.1, §2f): the 13 further subsystem programs of the Main Controller and the three Hub Controller programs (pitch error, pitch warning, rotor brake), the operating-mode mask (a bit string: 20 bits on the Main Controller, 6 on the Hub Controller), the task call frequency, the flags zero-load operation, availability calculation and the five Hub flags (each yes, no or not captured), and the numeric read and write levels of the 16 user-group slots. They are fields of the revision like any other: entered in the form (the sections *Further Program References*, *Operation Parameters* and *User-Group Levels*), shown on the detail page for the controller of the code, copied into every new revision and deprecation request, listed in the diff, the exports and the API (`user_groups`, `operating_mode_mask`, `operating_mode_bits`, `controller_type`), and never part of an audience export. A field that does not apply to the controller of the code (§2f) is refused with 422 and, in a program import, left out with a warning; a caller that does not send these fields (an older API client, a spreadsheet import) leaves them unchanged. The program import fills all of them from the file, except the five Hub flags, which stay *not captured* because the bit order of the Hub mask is not verified, and reads `loadless_spinning_permitted` from `ZeroLoadPrg_ArBo` (before v4.9 it wrongly took `ZeroLoadOperation_ArBo`). A named audience value brings the levels it held on every code that carried it (`default_read_level`, `default_write_level`, §9d.9) when the slot has none yet, and the CSV/XLSX import has columns for all of these fields (`user_group_levels` as `slot:read/write`, `operating_mode_mask` as a bit string); an empty or missing column leaves the stored value alone.
- **FR-169** The system shall show a **menu on the left** that is organised by the work of the user, collapsible and counted: the groups *Catalogue*, *Workflow*, *Import and Migration*, *Insight*, *Languages* and *Administration* (with the blocks *People*, *Configuration* and *Operations*), each link shown only to the roles that may use it (SEC-010), a *+ New Status Code* button for the roles that create codes, a badge on the links and a total on the group for what waits for the user (the review queue, the approval queue, stalled requests, withdrawn codes; one's own open change requests at their link), groups that stay open or closed as the user left them (the group of the current page always shows) and, below 768 px, where the menu used to be hidden altogether, a *Menu* button that opens it. The menu is defined as data (`app/ui/nav.py`), so that what each role sees is tested.
- **FR-170** The system shall mark a language **beta** in the language menu while no native speaker has reviewed it (FR-164): the mark stays until a review of the language is completed and for as long as a string awaits approval (FR-176). English, the source, never gets it. An Administrator can switch the mark off in the settings (`languages.beta_marker`, on by default). The mark is a hint to the people who read the interface, not a barrier.
- **FR-171** The system shall print the words around an export in the language of the export: the title page (heading, labels and values such as *not yet published* and *all*), the note on the digest, the column headings of the default PDF, the page footer and the banner of the working set. English, or no language, keeps the English text; the data rows, the field names of CSV, JSON and XLSX, the file names and the manifest are never translated. The words belong to the interface inventory (FR-167) and exist in all languages.
- **FR-172** The system shall show **only the reviewed languages to Viewers and to people who are not signed in**. While the mark of FR-170 is on, a language of which no review has been completed is hidden from the language menu, the login page and the account page of a Viewer and of a guest, cannot be chosen by them, and reads as English if a preference was stored earlier; a Viewer who was assigned a language to review (FR-164) still sees that one. Engineers, Reviewers, Chief Engineers, Administrators and the StCd Owner see every language, the unreviewed ones marked *beta*. Switching the mark off in the settings (`languages.beta_marker`) shows every language to everybody.
- **FR-173** The system shall export a Release as its **complete baseline**: every status code that is valid as of the Release - the latest published revision of each code in this Release or any earlier one - and not only the revisions the Release carries (roughly 900 codes of the Main Controller and 350 of the Hub Controller, so the manual of a Release is the whole catalogue). The delta stays available as *Changes of this release only* (`content=delta`). Every Release export, the offline lookup page and the package can be narrowed to a **turbine platform** (2XM, 3XM, 4XM) and to a **controller** (MC, HC); the baseline of a published Release never changes, and an unpublished Release shows the baseline it would have. The title page and the manifest name the scope. The Release page shows the counts (baseline, by controller, by platform) and, for working roles, how many codes are translated per language and how many have no confirmed access levels (information, never a block).
- **FR-174** The system shall build a **package** of a published Release in one step: a ZIP with the complete baseline in **every language** and for **every access level** (the eight audiences and the unfiltered file), in the chosen formats (PDF, XLSX, CSV, JSON), the release notes and a `MANIFEST.json` that lists every file with its SHA-256, row count, language and audience and the translation coverage per language. It can be narrowed to a platform and a controller. Everybody who may see the published Release may build and download it (FR-175); it is built in the background with a visible progress, recorded as an export with the SHA-256 of the ZIP, and audited (`PACKAGE_REQUEST`, `PACKAGE_EXPORT`). A code without an approved translation appears in the source language, marked in `content_language`.
- **FR-175** The system shall let **everybody who is signed in download what has been released** — the Release exports, the offline page, the release notes and the package of FR-174, Viewers included — and shall let **only the StCd Owner and the Administrator download what is not released yet**: the working set (FR-046) and the files of a Release that is not published. For anybody else an unpublished Release does not exist (404); the readiness check of FR-173 stays with the working roles.
- **FR-176** The system shall let **new and changed translations be approved separately**. What a native speaker approved stays approved: an OK answer, an accepted proposal (its final text), a rejected proposal or a noted question count as approval of that text, and the newest answer of a completed review wins. A string that is new, or whose text changed after it was approved (a shipped change, an accepted proposal that is edited, an override), is *awaiting approval*: the language keeps its *beta* mark for the working roles while any string awaits approval, a **follow-up review** lists only those strings (with *All translations* one click away) and is completed when each of them has a verdict, and a Viewer or a guest reads those strings in English until they are approved - the rest of the language stays in the language they chose. A language that no review has ever completed stays hidden from Viewers and guests (FR-172). The overview shows the number of strings awaiting approval per language.
- **FR-177** The system shall **check the confidence of the translations** whenever the text or the technical nomenclature changes, and show the result. Every string is checked mechanically (placeholders, missing or untranslated text, terms that differ from the nomenclature), a sample of 160 strings per language is read for meaning, register and consistency, and the result is a percentage per language: the share of strings a native speaker is expected to accept unchanged. A change of a string or of a term must be read one by one and recorded (`scripts/translation_precheck.py --check`, `--delta`); a test fails while a change is not covered. The overview (S42) and the catalogue document show the percentage on a colour from red (50 % or less) through yellow to green (above 95 %). The percentage is an estimate by a checker, never a review: it does not remove the *beta* mark and does not approve anything.
- **FR-178** The system shall **test every change of the vocabulary automatically and tell the StCd Owner which languages it touches**. A change that ships with a version (new or changed interface text, a changed term of the seeded nomenclature) is caught by the test of FR-177 in the build, and when the server starts - and with `flask translation-impact` after a deployment - the StCd Owner receives an in-app notice with the number of changed strings per language, whether the nomenclature changed, and the reviewed languages whose strings now await a follow-up review (FR-176). A change made in the application (a term added or changed, the translation of a term approved) is checked against every language at once - no approved translation, interface strings that do not use the term, reviewed languages affected - and the notice goes to the StCd Owner and to the reviewers assigned to an affected language. A notice is sent once per change and person, and a failing notice never undoes the change it reports.
- **FR-179** The system shall show **how status codes are connected**, as far as the generated programs say so. From every imported program three kinds of connection are read, as text and never by interpreting the controller logic: a code is *suppressed by* another when its set condition holds the other's active flag behind a NOT (the other is the *cause*, this one a consequence that is silenced while the cause is present); a code is *only set while* another is active when the flag appears without a NOT; a code *escalates to* its repeat code (`RepeatStCdArUi`), which mostly lies in a pool outside the catalogue and is then marked *external*. The code page shows, for working roles, what the code depends on, what depends on it and the chain of causes above it; the page *Connections* shows the causes with the codes they suppress as a tree, the escalation targets with the codes that escalate to them, and what looks wrong (a cause that is not in the catalogue, a deprecated or archived cause or escalation target, a loop of suppressions). The connections are derived from the newest imported program of each code, so a re-import changes them; an imported Draft is shown under the number it has reserved. The API gives both views (`/status-codes/{id}/connections`, `/status-codes/connections`). Viewers do not see them (as the where-used panel).
- **FR-180** The system shall let the people who hold each step work on a **whole batch of codes at once without weakening the step**, so that the first migration of ~900 Main and ~350 Hub Controller codes can pass the governance. On the *workbench* of a change set: the *readiness* of every Draft (what still stops it: no platform, the domain sign-offs pending); **bulk edit** of the same value on many Drafts (status category, platforms, available group, the eight access levels), only by the author or an Administrator; **bulk submit** of the Drafts of the author; **bulk domain sign-off** by a holder of the domain; and the bulk decisions of the Reviewer, the Administrator and the Chief Engineer. Every code still goes through its own service call: its own segregation-of-duties check, its own audit entry and, for a decision, the password of the person (entered once for the sitting); a code the person wrote or has signed already is skipped and reported. A bulk **decision or sign-off on more than a handful of codes needs a sample inspection first**: the system draws a random sample of the batch, stratified by subgroup so that every part of the controller is looked at - 10 % of the batch but at least 8 codes by default, none for a batch of 5 or fewer (settings `bulk.sample_percent`, `bulk.sample_minimum`, `bulk.sample_above`) - and **the person who decides inspects it**, marking every sampled code OK or DEFECT (a defect needs a note). The decision is possible only with a sample that is complete, has no defect, was drawn by the same person for the same step and batch as it is now (the batch changed: a new sample), is not older than 24 hours and has not served a decision yet. One defect blocks the batch: the defective codes are sent back with the note as the reason (Reviewer, Administrator and Chief Engineer; a defective Draft is for its author) and a new sample is drawn from what is left. The sample, its seed, the person, every verdict and the decision are kept, the comment of every code decided with it names the sample, and the **dossier** of the change set (XLSX: the codes with their decisions, the samples with their verdicts, the audit entries) puts it in one document for an auditor. A decision of the Reviewer cannot be repeated by the same Reviewer on a code already signed.
- **FR-181** The system shall let the user give **each program of a `.st` import its own status category**. The program files carry no category but they carry an *alarm type*; on the upload form the user chooses a category for each alarm type (1, 2, 3) and a default for the types left open (I-65). The preview shows the alarm type and the proposed category of every program in a list the user can change per row, or for all ticked rows at once; the category chosen in the preview wins over the alarm type, which wins over the default. The API takes `alarm_type_categories` on the preview and `categories` (item key → category) on the confirmation; an unknown category is refused with 422.
- **FR-182** The system shall let an Engineer or Administrator **delete several of their own Drafts at once from the Status Codes list**: a tick box per own Draft, a select-all box in the header, a *Delete selected Drafts* button and, when the list is filtered to Drafts, *Delete all my Drafts of this filter* across every page. Each Draft goes through the single withdrawal of FR-026 (only its author, only while open, one audit entry each), so one that cannot be deleted is reported and never stops the others; a number that was already issued is kept (BR-001), one that was only reserved is given back (BR-026).
- **FR-183** The system shall offer a **dark colour theme** next to the light one, chosen by the user in the top bar (and on the login page) as *Automatic (system)*, *Light* or *Dark*. *Automatic* follows the operating system's setting and changes with it; the choice is kept on the device the user works on (it is not part of the account) and is applied before the page is first drawn, so the wrong theme never flashes. Both themes meet the contrast rules of NFR-010 (4.5 : 1) for every text and fill pair, status and role colours stay recognisable, a printout and every export (PDF, XLSX, CSV, ZIP) keep the light colours, and the theme needs no inline script (SEC-025 stays unchanged). Every colour of the interface lives in a named token, so a new screen cannot bypass the theme (guarded by a test).
- **FR-184** The system shall **show its version**, so that a user, an administrator and a monitoring tool can tell which build is running. The number (for example `4.14.1`) is written once in `app/version.py` and shown at the foot of the menu, at the foot of the login page, and as `version` in the answers of `GET /api/v1/health` and `GET /api/v1/health/ready`; `pyproject.toml` is kept equal to it by a test. The version is raised with every release together with the git tag; the REST contract keeps its own version in `openapi.yaml`.
- **FR-185** The system shall produce, for every release, **four PDF documents with the version in the file name**: the full documentation (`CSCM-Tool_v<version>_Full-Documentation.pdf`: every document of `docs/` with a contents list and bookmarks, the quick deployment guide, and the artefacts - the OpenAPI contract and the database schema - as appendices), the software description (`..._Software-Description.pdf`), the user manual (`..._User-Manual.pdf`) and the test report (`..._Test-Report.pdf`). `python scripts/build_docs_pdf.py` makes them from the Markdown sources into `releases/v<version>/` (committed with the release), without a browser or an office program, in the Noto fonts of the application; `python scripts/ci.py --pdf` does so after a green pipeline, so the test report is the one of that run. Every PDF carries a title page with the version, the date, the commit and a digest of its sources, and a footer with the version and the page number. The version is the one of FR-184. The catalogue of interface texts (`26-translations.md`, several MB) is left out unless asked for.
- **FR-186** The system shall produce, for every release, **two PowerPoint decks of its design** in English, built from real screenshots of the application with fictitious data: a short deck **for management** (what the tool gives, the three independent decisions, the migration, trust, languages and themes, releases, what was delivered) and a **walkthrough for the team** (design principles, login, the shell, every main screen, languages and right to left, light and dark, phone, the rules for new screens). `python scripts/build_showcase.py` builds both - `CSCM-Tool_v<version>_Design-Showcase-Management.pptx` and `..._Design-Showcase-Team.pptx`, into `releases/v<version>/` - from a throw-away copy of the application (its own database, never a real one), photographed with the headless Edge or Chrome of the machine; figures (tests, coverage, requirements, languages, what was delivered) are read from the repository, so the decks follow every release. A text that does not fit its box stops the build; `--previews` shows every slide as the build sees it; `--pdf` (always given by `ci.py --showcase`) writes a PDF copy of each deck beside it, so a release holds each deck as `.pptx` and as `.pdf`.
- **FR-187** The system shall carry its **identity** the same way everywhere. The full name is **Controller Status Code Management Tool** (short: CSCM Tool) and appears on the title page of every release document and deck; **on top of every title page** stand the Software Owner and Administrator, Bastian Ritter, with the e-mail address bastian.ritter@senvion.in; and a **logo** - a wind turbine whose hub is a status ring, between code brackets, above three status lights - heads the title pages and appears in the menu bar, on the login page and as the icon of the browser tab. The names are written once (`app/branding.py`); the Git account and the repository are not named anywhere (the address of the repository is given by the Software Owner or the Administrator).
- **FR-188** The system shall be handed over to a team repository by a **repeatable, audited procedure** (`scripts/handover.py`, docs/15 section 9). The first release of a team repository is a *clean start*: the tree of the release tag becomes one commit on `main` with the author the owner names, plus the annotated tag; the history of the development machine is not carried over. Before anything is exported the tree is audited and any finding stops the hand-over: the Git account or repository name, keys and tokens, databases, `.env` files, paths of a personal machine, e-mail addresses other than the owner's, files over 5 MB, a version that disagrees with the tag, missing release files, a test report that is not green. The push needs the address of the repository, `--push` and `--yes` together and is never forced.

## 2. Non-Functional Requirements

### 2.1 Performance — NFR-001
Targets (13-test-strategy.md §5): 500ms p95 list/search at 20,000 revisions, 200ms p95 single-record read, 5s CSV/JSON export of 5,000 records, 15s PDF export of 5,000 records — now additionally validated for identifier-allocation contention within a single popular Functional System Group under concurrent submission (TC-025).

### 2.2 Availability — NFR-002
99.5% monthly availability during business hours, ≤ 4 hours/month scheduled maintenance.

### 2.3 Security — NFR-003
See 11-security-architecture.md. Summary: TLS 1.2+ only, on the internal network exclusively; no plaintext password storage/logging; CSRF protection on all state-changing endpoints; input validation and output encoding against injection; **no dependency on any public-cloud service, including for authentication, storage, or logging (NFR-003a, new in v2)**.

### 2.4 Scalability — NFR-004
The architecture supports ≥ 50 concurrent named users and 20,000 revisions without breaching NFR-001; repository pattern preserves a PostgreSQL migration path.

### 2.5 Maintainability — NFR-005
Layered structure per 15-development-standards.md, business logic in the service layer, ≥ 80% line coverage on service-layer and validation code.

### 2.6 Auditability — NFR-006
100% of state-changing actions (now including three decision points and sandbox create/delete) produce a corresponding audit log entry; retention ≥ 7 years, with the explicit sandbox-delete exception documented in 12-audit-compliance.md §3.

### 2.7 Usability — NFR-007
Core workflows completable by a trained user without external documentation; desktop-primary responsive layout, now `max-width: 1280px` per the OneTool design system (10-ui-ux-specification.md §0). Two requirements added 2026-09-17, direct responses to documented legacy-tool complaints: **NFR-007a** no form in the application may discard already-entered data as a result of a validation failure, network retry, or session event — a failed submission returns field-level errors only, never a reset form (10-ui-ux-specification.md §4 S5, §9). **NFR-007b** every lookup-backed field must surface its selected value's description as inline help text, so a user is never left choosing between unexplained options (10-ui-ux-specification.md §5).

### 2.8 Deployment Independence — NFR-008 (new in v2)
The system shall be deployable and fully operable on an isolated internal network with no outbound internet connectivity whatsoever — no feature in MVP scope may require reaching an external service to function. This is stricter than "no cloud dependency" alone: it is a testable claim (14-deployment-architecture.md §1) that the application continues to operate correctly with egress blocked entirely.

### 2.9 Multi-Process Readiness — NFR-009 (new in v4, I-20)
Several worker processes may serve one SQLite file. Everything that must be consistent across them lives in the database, not in process memory: the login rate limit (10 attempts per IP per 5 minutes, 5 per username per 15 minutes) is counted in `login_attempt` inside the login request's write transaction, so it is shared between processes and survives a restart. Concurrent writers queue on SQLite's write lock (`BEGIN IMMEDIATE`, 15 s busy timeout) instead of failing; the lock wait is measured (FR-153). Proven by running two real server processes against one file (13-test-strategy.md §8a).

### 2.10 Accessibility — NFR-010 (new in v4, I-22)
The interface meets WCAG 2.1 level AA: text and badge colours reach a contrast ratio of at least 4.5 : 1, every page has one `main` landmark, a skip link, a language attribute and a single heading hierarchy, every form control has a label or accessible name, table headers carry `scope`, state is never conveyed by colour alone, and the style sheet honours `prefers-reduced-motion`. Checked on every page in both languages by an automated test (13-test-strategy.md §8a); a manual screen-reader pass remains part of the pre-go-live checklist.

### 2.11 Observability — NFR-011 (new in v4, I-21)
Every request is logged as one JSON line with a request id (stderr, optionally a rotating file); `GET /health` (liveness), `GET /health/ready` (readiness) and `GET /metrics` (internal network only) let the on-premises monitoring see rates, latencies, write-lock waits, queue sizes and the state of the last verified backup. No telemetry leaves the network (NFR-008).

### 2.12 Recoverability — NFR-012 (new in v4, I-09)
A verified backup is taken at least nightly (RPO ≤ 24 h, ≤ 1 h with WAL shipping), the shipped schedule keeps 35 generations (the command's own default is 14), and the restore procedure is rehearsed quarterly (14-deployment-architecture.md §6–§7). The readiness probe reports `degraded` when no verified backup is younger than 36 hours (configurable).

### 2.13 Packaging & Continuous Verification — NFR-013 (new in v4, I-33)
The application installs from a checkout with one script per platform (Windows Server scheduled tasks; Linux systemd units), upgrades idempotently, never overwrites configuration, data or backups, and takes a verified backup before migrating an existing database. A CI definition for the on-premises Git server runs the whole verification (tests in a rotating order, coverage, black, ruff, mypy, bandit, pip-audit) on every push; the install scripts are syntax-checked and dry-run in the test suite.

### 2.14 Database Portability — NFR-014 (new in v4, I-34)
SQLite-specific constructs (triggers, `BEGIN IMMEDIATE`, `GLOB`, FTS5, the online-backup API, `sqlite3` calls) are inventoried by `scripts/pg_readiness.py`, each with its PostgreSQL porting note, and counted against a committed baseline: CI fails when a change adds SQLite-specific code, and when one is removed until the baseline is lowered. Engine set-up is already guarded by dialect. The application has **not** been run on PostgreSQL; that is the Phase 3 port this requirement keeps cheap (07-database-design.md §12).

## 3. Business Rules

- **BR-001** A Status Code's identity is immutable once its identifier is allocated; it cannot be changed by editing, only superseded via deprecation.
- **BR-002** A Status Code has at most one revision flagged `is_current = true` at a time.
- **BR-003** Only one open (Draft, Review, or PendingApproval) revision may exist per Status Code at a time.
- **BR-004** A revision cannot transition to Released except via inclusion in a published Release, cannot reach Approved except via explicit Chief Engineer approval, and cannot reach PendingApproval except via both the Reviewer's and the Administrator's independent sign-off.
- **BR-005** No individual may both author and decide on the same Change Request at any of the three decision points (Reviewer sign-off, Administrator sign-off, Chief Engineer approval); the Chief Engineer additionally may not be whoever provided either of the two prior sign-offs on that CR.
- **BR-006** Deprecating a Status Code requires a reason; archiving requires the configured minimum retention period (default 180 days) to have elapsed since deprecation.
- **BR-007** A published Release's member revisions are immutable; correcting a released status code requires a new Draft revision, a new full three-decision-point cycle, and a new Release.
- **BR-008** Only Administrators may create, publish, or delete (pre-publish only) Releases.
- **BR-009** Viewers have read-only access to Approved, Released, Deprecated, and Archived data; Draft, Review, and PendingApproval-state data is visible only to Engineer, Reviewer, Administrator, and Chief Engineer roles.
- **BR-010** A sandbox-flagged Status Code may never be included in a Release, and is the only category of record that may be permanently deleted, and then only by an Administrator.
- **BR-011** Submit-for-Review is blocked while any Engineering-Domain-owned field lacks coverage from either the originating Engineer's own domain tags or a recorded `DomainSignoff`.
- **BR-012** Each of the eight audience-access fields (corrected 2026-09-17; replaces the single `access_rights_id`) is not authoritative until confirmed by the Administrator's Review sign-off, regardless of what value the originating Engineer proposed.
- **BR-013** A Status Code must have exactly one Functional Subgroup at all times; Functional Subgroup is never optional (corrected 2026-09-17).
- **BR-014** A new Functional Subgroup's sub-range must not overlap any existing subgroup within the same Functional System Group.
- **BR-015** Every row imported via the library import feature must pass through the full Change Request lifecycle before Release; import creates Drafts only, never Approved or Released records directly. This holds for every import mode, including update mode (FR-048k) and Hub-to-Main carry-over (FR-147).
- **BR-016** (v4) An audience sees a code only if the Administrator-confirmed value of that audience's access field is marked *visible*; a missing value hides the code, and `Covert` is not visible until the business defines it otherwise (decision D-02). A Draft's proposed values never count (BR-012).
- **BR-017** (v4) A delegate acts as themselves. Delegation grants the decision actions of the delegated role only; the segregation-of-duties rules (BR-005) apply to the delegate personally, the two Review sign-offs must still come from two different people, and the audit entry names the delegate and the person they cover for.
- **BR-018** (v4) A translation is approved by one Reviewer or Administrator who is not the translator; it is not subject to the three-decision cycle of the source text, and editing an approved translation returns it to DRAFT.
- **BR-019** (v4) A save of a Draft that is based on an outdated `row_version` is refused and changes nothing (FR-090); a Released revision is never edited in place (BR-007).
- **BR-020** (v4) Audit entries are never deleted: archiving writes a copy and an `AUDIT_ARCHIVE` entry (FR-151), and any gap, edit or reordering in the hash chain is a reportable integrity failure.
- **BR-021** (v4) A Release may target one or more controller software versions, set by an Administrator before publishing. When it has targets, its candidate list holds only Approved revisions whose version range includes at least one target (an open end includes everything); with no targets every Approved revision is a candidate. The target versions of a published Release are immutable like its items (BR-007), and a revision's range is otherwise informational — it never blocks a lifecycle transition.
- **BR-022** (v4) A sensitive action — Reviewer or Administrator sign-off, Chief Engineer decision, publish, full-database export — needs a fresh password confirmation from the actor, unless the deployment deliberately turns step-up off (`STEP_UP_REQUIRED`, a documented deviation).
- **BR-023** (v4.2) A number that an imported program already carries is reserved for exactly one status code and is issued to that code unchanged at Submit for Review: no other code can be allocated or overridden to it, the code itself cannot be given another number, and the mapping from its legacy number to the new one is never inverted (FR-048q, FR-048u).
- **BR-024** (v4.3) Only an Administrator creates users and gives or takes away the roles Administrator, StCd Owner and Chief Engineer. An StCd Owner may change a user's role only when the user holds Viewer, Engineer or Reviewer now and is to hold one of those three afterwards; the service layer refuses everything else with 403, and every change is audited as `ROLE_CHANGE` with the actor. The last active Administrator can never lose the role (FR-012).
- **BR-025** (v4.6, changed in v4.9) An Administrator can delete every account, and the audit log is never modified. An account that nothing else points at - no change request, review, release, audit entry or any other record - is **removed**, with its own rows (domain tags, password history, saved searches, notices). An account with history is **erased**: its user name becomes `deleted-<id>`, its address `deleted-<id>@deleted.invalid`, its name *Deleted user*, its password is destroyed, its own rows and reviewer assignments go, `user.deleted_at` is set, and it leaves every list and every call (404). The row stays, so every record it created still has an author and every audit entry still resolves its actor; the old user name and address are free again. The deletion is audited as `USER_DELETE` with the snapshot of what the account held and the mode (`removed` or `erased`). Deactivating, which keeps the name, remains the gentler choice.
- **BR-026** (v4.6) Withdrawing a change request never reuses an issued number: a code that already received its identifier keeps it. A code that never did gives back the number an import reserved for it, its legacy number and its PrgIdx_GUi, because nothing was issued and the same program has to be importable again. A code whose last revision was withdrawn is an empty shell (`status_code.withdrawn_at`) that keeps its number, legacy number and PrgIdx_GUi and so blocks the same program or row from being imported again (v4.9). An Administrator can **delete such a code** on the page *Withdrawn Codes* (S48), with the password again. The deletion is done in place (`status_code.deleted_at`): the row stays, so no id is ever reused and every audit entry keeps pointing at one code, but the code gives up its identifier, reserved number, legacy number and PrgIdx_GUi, and the program or row can be imported again. It is audited as `WITHDRAWN_CODE_DELETE` with what the code held. The database trigger refuses every delete of a non-sandbox code, so a code that has ever had a revision (and so may have been Released) is never touched. A number freed this way can be allocated again if it was the highest of its range; restoring the code from its program file instead clears the withdrawal mark.

## 4. Constraints

- **C-001** MVP persistence is SQLite (single-file, file-based); this bounds MVP concurrent write throughput and requires the repository-pattern abstraction (NFR-004) to enable a later migration. SQLite is not intended as a permanent production datastore; see 16-mvp-roadmap.md for the Phase 3 migration trigger.
- **C-002** MVP authentication is session-based, internal user store only; on-premises AD/ADFS integration is out of scope for MVP (FR-005).
- **C-003** Backend framework is fixed to Python/Flask; frontend is server-rendered HTML/CSS/vanilla JavaScript, no external CDN dependency (11-security-architecture.md §12).
- **C-004** The application must run in the target on-premises deployment environment described in 14-deployment-architecture.md.
- **C-004a** No public cloud (SaaS/PaaS/IaaS) component may be introduced at any phase without an explicit, separate decision to relax C-004 (new in v2 — see 00-INDEX.md "Deployment Principle").
- **C-005** *(superseded 2026-09-17 — retained for history)* The original position was that no bulk import feature would exist in MVP. The business has since explicitly requested CSV/XLSX library import (FR-048a–d) to support the legacy migration; the constraint now is that import must never bypass governance (FR-048c), not that import must not exist.

## 5. Assumptions

- **A-001** The initial user population is small (tens, not thousands, of named users across all six roles), consistent with NFR-004's 50-concurrent-user target.
- **A-002** Engineers, Reviewers, Administrators, Chief Engineers, and Viewers are employees or contractors with existing corporate accounts; user provisioning is manual (Administrator-driven) until on-prem AD/ADFS integration lands.
- **A-003** Status code catalogues across all nine Functional System Groups remain in the low tens of thousands of revisions over the system's MVP lifetime, consistent with NFR-001's sizing.
- **A-004** Technical Publications and any future SCADA/documentation-generation consumers will integrate against the versioned REST API or scheduled exports, over the internal network only; no direct database access will be granted to external systems.
- **A-005** The organization has an existing password/credential policy that CSCM Tool's password rules (11-security-architecture.md §4) can align with.
- **A-006** The real Functional Subgroup taxonomy, supplied 2026-09-15 and seeded directly (06-data-dictionary.md §9a), is treated as authoritative; any further changes Controls Engineering makes before go-live remain a data-only update. The `10000–10999`, `14000–14999`, `15000–15999`, and `16000–16999` ranges are confirmed free/reserved capacity, not an outstanding classification gap.
- **A-008** (new 2026-10-22) The Hub Controller (HC) may be removed from the hardware setup in future. If so, the status codes of the functions it carried move to the Main Controller (MC) side and are **defined there anew** — they are new MC codes in MC groups/subgroups, not renumbered HC codes. The design must therefore keep Hub groups as ordinary data (deprecatable, no code paths that depend on the 11000–13999 range) and make it easy to create new MC groups/subgroups; see I-36 in 21-improvement-ideas.md.
- **A-007** Chief Engineer is a distinct, sufficiently-staffed role in the organization such that the added approval step does not become a single-person bottleneck; this should be validated against actual staffing before go-live (16-mvp-roadmap.md §6 risk).
- **A-009** (v4) Technical Publications can use an internal SMTP relay for reminders if the business wants mail; until that is confirmed, in-app notices are the whole mechanism (decision D-04). Mail is never required for any workflow step.
- **A-010** (v4) The meaning of `Covert` in the audience vocabularies is still unconfirmed; the system treats it as *not visible* (D-02) so that a wrong guess can only hide a code, never disclose one.
